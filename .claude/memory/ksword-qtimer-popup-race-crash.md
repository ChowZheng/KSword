# QTimer::singleShot 驱动 QMenu/QDialog exec() 的两个坑（wpH 波二实测）

- 起因：wpH 波二把审核者补测（T12/T13，驱动右键菜单的 `QTimer::singleShot(固定毫秒, [&]{...})`）
  并入夹具后，**实测复现过一次真崩溃**（`exit=-1073741819` / `0xC0000005` 访问越界）加一次
  确定性失败，均与"用固定延时的嵌套定时器驱动阻塞式 `exec()`"这套写法有关。
- **坑一（会崩）：嵌套第二层 `QTimer::singleShot` 按引用捕获本函数局部变量**——外层定时器
  在 `menu->exec()`/`dialog->exec()` 的嵌套事件循环里触发，若它的处理逻辑在"预期分支"下
  会提前让 `exec()` 返回（没有第二层 `exec()` 续命），外层函数几乎立刻返回、栈帧销毁；
  但外层定时器自己还注册了一个"再过 N ms 检查一次"的**第二层**定时器，这个定时器按引用
  捕获的局部变量此刻已经不存在——它迟早会在某次毫不相关的事件循环（可能是下一个用例自己的
  `exec()`/`qWait`）里触发，对已销毁的栈变量写入。判据：进程本身没有任何测试断言失败，
  直接整进程崩溃，日志最后一行停在某个无关的"下一个套件正常输出"之前。
  **修法**：只用一层定时器；若确实需要"过一会儿再确认一次"，让外层函数自己在 `emit`/`exec()`
  返回之后显式 `processEvents()+qWait()` 排空事件循环，再检查全局状态（`activeModalWidget()`/
  `activePopupWidget()`），不要再嵌套第二层定时器。本仓库 `wpH_tests.DisasmRegression.cpp`
  的 `runD10Tests` 已经是这个安全写法（单层定时器 + 之后显式排空），新写的测试应该抄它，
  不要抄审核者 `extra2.cpp` 里那个带第二层嵌套定时器的版本。
- **坑二（会假失败，不崩）：固定延时数值在机器负载重时会错过 `exec()` 真正进入嵌套循环、
  弹出控件变成 `activePopupWidget()` 的那个窗口**——哪怕延时已经放宽到 450ms/8s 看门狗，
  在本机"同时有别的包在构建"时仍然偶发读到 `activePopupWidget()==nullptr`（菜单其实还没
  被判定为活动弹出，或者判定窗口已经错过）。**修法**：探测回调改用 `QTimer::singleShot(0, ...)`
  而不是猜一个毫秒数——0ms 定时器仍然要经过一次事件循环分派，但只要 `exec()` 已经进入它
  自己的嵌套循环，这个回调必然会在第一轮就被处理，不依赖具体墙钟时长，完全不受机器忙闲
  影响；看门狗（真正兜底关闭，不检查任何局部状态）可以继续用一个大一点的固定延时（2–8s）。
  实测：改成 0ms 之后连续 8 次整套件重跑 0 failures（之前固定延时版本 4 次里能看到 1–4 次
  不等的假失败/崩溃）。
- 两个坑同源：**凡是要靠 `QTimer::singleShot` 从外部"戳一下"正在运行 `exec()` 的阻塞对话框/
  菜单的测试，都应该用一层定时器 + 0ms 延时触发交互 + 交互做完后显式排空事件循环再读结果**；
  "审核者/上一轮写的测试已经验证过"不等于它在并入更大的夹具、与其它用例共享同一个事件循环、
  且机器更忙时还是安全的——合并测试时要重新审视这类定时器写法，不能照抄。
