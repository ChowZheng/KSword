## 0. 构建方法（**必读，否则编译会卡住**）

纯 Win32，无 CMake，只能走 `KswordARKLight.vcxproj`：

```
D:\Software\VS\MSBuild\Current\Bin\MSBuild.exe
  E:\Projects\Ksword5.1\KswordARKLight\KswordARKLight.vcxproj
  /p:Configuration=Release /p:Platform=x64 /m
```

两个坑，已在 `.workbuddy/tools/build-arklight.ps1` 里封装好（直接调这个脚本即可）：

1. **代理变量冲突**：宿主进程同时导出 `HTTPS_PROXY` 和 `https_proxy`，.NET 的
   `ProcessStartInfo` 建字典时抛 `MSB6001` → 编译前必须清掉大小写重复的代理变量。
2. **驱动构建会弹签名窗**：standalone 构建默认 `BeforeTargets` 链到
   `KswordARKDriver.vcxproj` 再执行 `Sign-KswordArkDriverVariant.ps1`，需要交互式证书。
   加这 4 个属性可完全跳过（前提：`Ksword5.1\x64\Release\KswordARK.sys` 已存在）：
   ```
   /p:KswordArkLightEnsureDriverBuilt=false
   /p:KswordArkLightReuseSignedDriver=true
   /p:KswordArkLightSkipDriverSign=true
   /p:KswordArkLightSkipRestoreCleanDriver=true
   ```

增量编译约 15–25 秒。

## 5. 附录：CLI 门禁的现成方案（交给逻辑侧，不必重新调研）

**根因**：注册表把 legacy 语法存进 `legacySyntax`（`CommandRegistry.cpp:112-114`），
`KswordCLI.cpp:1414-1441` 却拿 legacy 语法做参数白名单 → `kernel ioctl query-basic`
这类现行命令必然报"非法参数"，而 `force-unload-driver` 等破坏性命令**不带任何确认就能跑**。

**正解（两层校验，方向相反）**：
- 助手 `IsKnownOptionToken`（`KswordCLI.cpp:297` 的 `knownFlags`）保持"宽容"：`Ctrl::kCommandSyntax` ∪ `legacySyntax`，
  因为值位里的 `-` 开头字符串不该被误判为未知选项。
- 守卫 `requireConfirmOption`（`:1254-1278`）保持"严格"：只查 `Ctrl::kCommandSyntax` ∪ 别名
  `{--yes, --assume-yes}`。**不要 `|= legacySyntax`**，否则 `printer locate --help` 这类合法命令会被要求确认。
- 需要补门禁的 4 处：`force-unload-driver:5539`、`callback remove(-ex):6006`、`file delete-path:4988`、
  `process terminate:2631`；并移除 `memory write-*:2996/3054` 默认携带的 `UI_CONFIRMED` 位。
- 白名单修正后 `--confirm` 成为合法选项，"主动传确认反被拒"的矛盾自然消失。

**破坏性变更（需产品确认）**：同一调用族将统一要求确认——`process terminate` 走 `dispatchR3`、
`process kill` 走 `dispatchLegacy`、`driver force-unload-driver` 走 R3、`driver force-unload` 走 legacy，
改完这 4 个命令共 8 条路径都会开始报"缺少 --confirm"。这是本轮唯一会破坏既有脚本行为的改动。

**取证脚本**：`Test-KswordCLIReadOnly.ps1:207-226` 的正则已落后于新 help 格式，脚本当前必然
throw（`$supported` 为空 → `:631-634`），只读防线实际不存在；修脚本前不要相信它的"通过"。
