## 2 缺陷根因目录（12 簇，按严重度排序；【已核实】=主会话直接读代码确认）

1. **【高·已核实】状态分裂，无单一目标会话**：进程/后端/地址/快照散落 ≥10 处独立状态（附加五元组、模块预览缓存、Tab5/Tab3 各自的快照字段、4 个互不联动的后端下拉、DDMA 会话）。症状：选中 B 进程的模块却用来读 A（nav N-02）、换后端不触发重读（viewer V-02）、断点写错进程（nav N-03）。涉及：nav、viewer、flows、hosts、driverrw 全部提及。
2. **【高·已核实】行号当稳定 id，遇排序即错位**：搜索结果表 `setSortingEnabled(true)`（`MemoryDock.UiBuild.cpp:1024`，本会话已核实）+ 代码按 `row` 下标取缓存（`m_searchResultCache[row]`）；Hex 表从未调用 `SetTableHeaderClickSortingEnabled`（本会话核实：仅 `MemoryEditorWidget.cpp:145,198` 给指令/对比表关闭，Hex 自己的表没有），被全局表格设施自动装上点击排序。症状：排序后双击/加书签/编辑作用于错误地址（nav N-01、flows F01、hex H01）。
3. **【高】固定小窗口，无翻页/连续地址空间**：Tab3 查看器硬编码 512 字节窗口、起点=目标地址（不对齐），全仓无翻页控件；Tab5 虽上限 1 MiB 但也是"手改中心地址"模式，非连续浏览。这是与 CE/x64dbg 核心体验差距最大的一点（viewer V-01、hex 建议§5、editor E-03、hosts H-01、flows F05、nav N-15）。
4. **【中高】全表重建渲染，无虚拟化（未实测，按代码路径推断）**：HexEditorWidget 每字节一个 `QTableWidgetItem`，任何编辑/翻页/撤销都 `clearContents()` 后重建全部；Tab5 上限 1 MiB≈118 万 item，FileDock 2 MiB≈236 万。重写前应用离屏 Qt 微基准实测（hex H05、editor E-23、hosts M-12）。
5. **【高】编辑原语贫乏**：唯一编辑方式是"两位十六进制+Enter"逐字节提交；无粘贴、填充、NOP、选区整体赋值、ASCII 列编辑、类型化写值（整数/浮点/字符串，字符串写入只存在于 Tab5 一处对话框）。改 4 字节需 4 次独立提交（hex H04、editor E-01、viewer V-17、flows F09）。
6. **【高】选区状态三头不同步**：Qt 原生 selectionModel、`m_selectionRange*` 成员、单元格背景画刷三套并存，键盘导航/跳转/改行宽只更新其中一套。症状：方向键后 Ctrl+C/右键仍用旧选区（hex H02）。
7. **【高】"断点"名不副实、生命周期失控**：直接裸写 0xCC，程序内无调试事件循环，`hitCount` 恒 0 却宣称"执行到该处时会中断"；断点表不绑 PID，分离/换进程不清理也不还原原字节（viewer V-04/V-05、nav N-03、flows F03）。目标进程会因此崩溃，且旧进程留有未还原的 int3。
8. **【中】书签功能贫瘠且不绑上下文**：不持久化、不绑 PID/模块（换进程后指错地址）、值只读 8 字节十六进制串不可改、1 Hz 定时器无条件常跑（含可能触发磁盘 DMA 的 DDMA 轮询），不看页面是否可见（viewer V-16、nav N-18、flows F15）。
9. **【中】通道/后端默认值与文案不一致**："R0 读取"按钮实际默认走 R3（`UserMode`）；HVM 可用性从未在 UI 里检查提示；DDMA 不可用时静默弹回 R0（nav N-08、flows F04、viewer V-13）。
10. **【中】地址语法三套矛盾**：Tab3 地址栏默认十六进制且不支持模块+偏移；Hex 内 Ctrl+G 跳转面板"先十进制后十六进制"（纯数字按十进制，与行地址 0x 回显相反）；Tab5 支持 `module+offset` 但 Tab3 不支持；Hvm 系对话框另有第三套解析器（支持 WinDbg 反引号/下划线）（hex H08、editor E-15、viewer V-15、flows F08、infra D-05）。
11. **【中·已核实】写回确认策略不一致**：Tab3 应用无确认，Tab5 默认二次确认（可被全局"跳过危险确认"关闭，但协议层校验与审计日志仍跑，本会话已核实 `driverApplyMemoryDiffFromUi:1098-1144` 这一分层是正确的）；DDMA 写回的强制同意 `ddmaForceApproved` 定义在块级循环外、确认一次后对本轮其余全部块复用（本会话核实 `MemoryDock.DriverMemoryRw.cpp:1276,1289-1304`），与协议注释"必须逐次询问"相悖（viewer V-07、driverrw DR-02）。
12. **【中低】UI 堆叠与仓库规范违反**：Tab3 字节表上方叠 ≥7 条横带（导航行/后端条/应用行/编辑器工具行/状态行/内层页签/Hex 工具行）；`MemoryEditorWidget` 顶栏按钮全是文字（违反"简单含义用图标"规范）；文本页/对比页用 `QPlainTextEdit` 而非仓库规定的 `CodeEditorWidget`；多个文件超 1000 行约定（`MemoryDock.ProcessRegion.cpp` 2533 行等 12 个文件，`wc -l` 实测）（viewer V-18、editor E-16、infra D-06）。

## 3 必须原样保留的不变式（重写不可破坏；每条给出违反后果）

| # | 不变式 | 违反会怎样 |
|---|---|---|
| 1 | 控件本身永不写目标内存，只改缓存并发信号；写前/写后校验在 owner | 一旦控件自己调写接口，只读转储场景（Dump/证据页）会意外获得写能力 |
| 2 | `setSnapshot`/`sourceIdentity` 只在"目标+后端+基址+长度"全等时保留上次读取，用于比较 | PA/CR3/PID 跨目标混比较会把无关地址的差异误报成"内存被修改" |
| 3 | 写前逐块复核原字节（与基线一致）→ 写 → 写后逐块回读 → 任一失败不报整体成功 | 覆盖掉其他程序并发写入的内容而不自知，或把"发出写请求"误报成"已确认写入" |
| 4 | 四通道（R3/R0/HVM/DDMA）不自动合并、不自动回退 | 同一地址不同通道给出不同答案本身是检测信号（内存管理器被挂钩/SLAT 重定向），合并即丢失这个判据 |
| 5 | 不伪造零字节：`ZERO_FILLED`/整段翻译失败判失败，不当成功数据 | 把"读不到"显示成"读到的都是 0"，逆向分析会把補零当成真实数据 |
| 6 | 部分读保留已读字节并明确标注"只读到 M/N 字节" | 用户以为拿到完整数据 |
| 7 | 内核写走 PREPARE→dry-run→FORCE→回读→回滚复核的事务链 | 内核内存修改无法回滚，可能导致不可恢复的系统损坏 |
| 8 | 地址默认十六进制、数量默认十进制，两者类型层面分离，溢出判失败不回绕 | 纯数字地址被当十进制读到错误位置（仓库里已踩过的坑，`ksword-address-radix-default.md`） |
| 9 | `MemoryEditHistory`：一次 `refreshFromHexEditor` 聚合为一步历史，32 MiB/256 步上限，失配整步拒绝，新编辑切断 redo 分支 | 撤销/重做出现"半成功"的中间状态 |
| 10 | `MemoryAssembly`：有界（64 KiB/4096 行/32 趟），失败不返回部分机器码，覆盖必须含完整旧指令边界 | 汇编失败却写入半条指令，破坏目标代码 |
| 11 | 内容代次守卫：模态对话框/延迟回调落地前复核代次+地址+架构 | 用户切换目标/撤销后，陈旧的异步回调把结果写到错误位置 |
| 12 | 变更高亮规则：橙=相对基线待提交、青=两次实际读取之差，引用与缓冲尺寸不符即不高亮 | 误导篡改检测——把程序自己的待提交编辑显示成"外部篡改痕迹" |
| 13 | 代次/ticket 丢弃陈旧异步结果（搜索、书签、模块枚举） | 切换目标后旧扫描结果混入新目标 |
| 14 | DDMA 会话代次绑定；暂存扇区脏即使成功也要告警（`scratchDirty`） | 磁盘上留下未还原的脏扇区而不通知用户 |
| 15 | "跳过危险确认"开关只跳 UI 阻断，不跳协议层强制标志与审计日志 | 关掉确认框的同时意外关掉了安全校验 |
| 16 | 异步读写用 worker 线程 + 代次丢弃，复制句柄给 worker 而非共享原始句柄 | UI 线程阻塞；owner 关闭后 worker 操作悬空句柄 |

## 5 重写边界建议

- **13 个页签的归属**：Tab0/1/2（进程/模块/区域/搜索，目标发现）与 Tab3/5（查看器/驱动读写）、Tab4（断点与书签）构成"内存编辑/显示器"工作流本体，是本次重写范围；Tab6/7/9（内核可执行页/内核内存证据/进程内存证据）是只读分析，建议保持独立但补上"在新工作台中打开"的跳转入口（目前完全没有，hosts M-08）；Tab8（PTE/VA 翻译）、Tab10（系统内存审计）、Tab11（篡改检测）是独立诊断页，不动；Tab12（DDMA）降级为新工作台的"通道设置"子面板。
- **HexEditorWidget 去留**：旧控件冻结供 FileDock/NetworkDock/DiskEditorTab 使用，不在其头文件上做破坏性修改（避免扇出重编译，也避免影响已稳定的非内存场景）；内存工作台新建一个自绘/虚拟化的 Hex 视图，通过门面层与旧 `MemoryEditorWidget` 的外部 API 兼容，让 9 个现有宿主逐个低风险迁移。
- **单一目标会话**：进程/后端/地址/架构从当前散落的 ≥10 处收拢成一个值类型（scope+pid+创建时间+通道+DDMA 代次+位数），Dock 持一份，Tab3/5 共用并持久化，不再各自维护一套。
- **断点**：要么接入仓库已有的调试器后端（`ksword-debugger-backend.md`）使其成为真断点并正确计数，要么明确降级改名为"int3 补丁"工具，不能保留现在"叫断点但没有调试循环"的状态。

## 6 验证基础设施

- **构建**：`tools/Invoke-KSwordBuildCheck.ps1`（HostX64 强制、两道构建期门禁 i18n+主题 token，各 ~2-18 秒，耗时数分到 7 分+），成功判据 `BUILD_RESULT=SUCCESS && EXIT_CODE=0` 且产物非零。
- **现有测试**：`Invoke-MemoryEditHistoryTests.ps1`（420 项）、`Invoke-MemoryAssemblyTests.ps1`（当前 250 项，含工作树未提交改动）、4 个 `tools/hvm_unit_tests/test_memory_*.py`（Python 按函数名抠生产源码编译，76/60/73/83 项）、`test_ddma_editor.py`（13 分支）——**全部不在 CI、不在套件清单**（`ksword-expected-suites.json`），只有 `KswordARKLightTests` 里登记的几个套件会被 CI 看见。
- **离屏截图**：无内存编辑器专用 harness；唯一先例 `tools/hvm_lab/build-ui-tests.cmd`（HVM 专用），缺 Svg DLL/qrc 对象/Highlight palette 角色/全局 QSS 基线，需要仿照补全才能用于视觉验证。
- **风险**：Python 抠函数测试按文件名+函数名正则绑定源码，重写搬文件/改名会让它们直接报错而不是误报通过；新增文件要同步 `.vcxproj`/`.filters`、双语言包并过 `i18n_language_pack.py audit`；语言包只能定点编辑。

## 7 需要用户拍板的决策点

1. **写入模式**（已拍板）：默认"改完立即写入"，提供可切换开关，暂存-应用模式作为可选项保留。
2. **断点功能去留**：接入已有调试器后端做成真断点（成本高，收益是功能名实相符），还是降级为"int3 补丁"工具（成本低，但失去"调试"语义）？推荐先降级改名，调试器集成作为后续独立项目。
3. **Tab3（查看器）与 Tab5（驱动读写）是否合并为同一个工作台**：现状是两份平行实现，合并能消除状态分裂（簇 1）但工作量显著更大。推荐合并，因为这是 nav/hosts/flows 三份报告一致指出的最大结构性冗余。
4. **旧 HexEditorWidget 的处理方式**：完全冻结只服务非内存宿主、内存工作台另起一个自绘控件（推荐，风险最低、不影响已稳定场景），还是改造现有控件使其同时支持两种用法（风险更高，但避免维护两套 Hex 实现）？
