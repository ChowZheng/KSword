# KSword 意外蓝屏与崩溃审计

审计日期为 2026-10-06。第一轮代码基线为 `bc583880`，续审跟进至远端 `bb55a043`。第一轮七类缺陷和续审确认的问题均已完成源码修复，具体触发条件、功能影响和验证结果如下。

用户明确要求保留实验性 Bugcheck Guard、HVM 睡眠转换和线程终止 APC 的现有行为；这三项不属于本轮自动修复范围。其边界仍保留在下文。源码修复和离线验证尚不能替代完整构建和目标机验收。本次没有加载驱动、启用虚拟化、触发蓝屏或修改运行机器的内核状态。

## 已修复的问题

| P1 | 启动期进程偏移探测 | 导出解码得到错误偏移或 SectionObject 候选 | 对不可信字段或对象头直接访问，可能导致驱动加载时内核页故障 | 不再猜测 SectionObject；已有精确 profile 直接使用，其他候选字段走安全读取 |

| P1 | HardwareDock 后台采样 | 采集期间关闭页面或程序 | QPointer 非空检查后，窗口仍可被释放；投递和失败回写可能访问悬空对象 | 三条任务使用全局线程池和应用接收器，仅在 UI 回调访问页面 |
| P1 | HTTPS 服务和会话停止 | 证书任务超过会话等待上限，或 finished 与后台 wait 并发 | 继续访问已释放服务和锁，或等待已经被删除的 QThread | 共享证书状态、线程强引用快照、受锁保护的 UI 投递关闭边界 |
| P1 | HUD 静态和传感器采集 | 采集期间快速退出 HUD | 与 HardwareDock 相同的窗口接收器和后台回写竞态 | 两条任务使用全局线程池和应用接收器 |

| P1 | 工作台目标同步通知 | 附加、分离或钉住目标时，通知订阅者同步销毁目标 | 通知返回后继续访问 tracker 和模块目录 | 三个入口在通知后检查 QPointer，销毁后立即停止 |

### 交叉视图引用候选对象

涉及 [process_crossview.c](../KswordARKDriver/src/features/process/process_crossview.c)、[thread_crossview.c](../KswordARKDriver/src/features/thread/thread_crossview.c) 的候选引用包装，以及既有 `KswordARKObjectHeaderReferenceObjectSafe`。

旧进程路径先 `ObGetObjectType` 再 `ObReferenceObjectByPointer`。线程路径虽然已有按 ID 查询的 helper，但调用 helper 前仍读取了未经引用的对象头。对象退出和错误候选地址会使这些操作缺乏生命周期保障；外围异常处理不能把任意内核地址变成可靠对象。

修复后的成功条件是公开 ID 查询取得引用、返回对象地址等于观察到的候选、引用后类型校验通过。失败时不访问候选对象头，也不设置已确认类型或已取得引用的标志。来源明确的进程链或线程链仍保存未确认候选证据；混合 CID 来源中无法确认类型的行不会冒充进程或线程。其代价是无法通过公开查询安全引用的隐藏对象，不再靠猜测指针补全类型。

### 启动期进程偏移探测

涉及 [process_resolver.c](../KswordARKDriver/src/platform/process_resolver.c) 和 [dyndata_loader.c](../KswordARKDriver/src/features/dyndata/dyndata_loader.c)。

旧 SectionObject 解析从导出代码中猜测字段偏移，直接读取字段后把猜测指针交给 `ObGetObjectType`。检查对象主体首尾地址驻留不能证明对象头有效或对象仍存活。加载器将解析器作为函数实参，已有 profile 偏移时也会先执行这条猜测路径。

现在只在字段不可用时求值 fallback，已有精确 profile 的偏移和来源保留。没有可独立引用的 Section 锚点时，解析器返回不可用，不读取猜测对象或调用对象 API。因此缺少该字段的 profile 会显示不可用，关闭的是该字段的启发式补全；没有恢复全局 OS build 上限。

同文件的五处导出机器码快照和签名、Section 签名、Protection 三个候选字节统一使用 `KswordARKRuntimeReadMemory`。不可读或值与真实访问器不一致时拒绝偏移，异常处理只保留给真实访问器调用。

### AMD 常驻资源与电源回调

涉及 [hvm_runtime.c](../KswordARKDriver/src/features/hvm/hvm_runtime.c) 的 `KswordARKHvmBeginBackendContextMutation`、准备和资源释放分支，以及 [hvm_svm_lifecycle.c](../KswordARKDriver/src/features/hvm/hvm_svm_lifecycle.c) 的 `KswordSvmStop`。

旧 Stop 在取得 transition phase 前就保存 `BackendContext`；AMD 资源准备和释放不持有该 phase，因此 CPU 账本可能在 Stop 广播时被部分建立或销毁。修复先发布 `ResidentContextPreparing`，再短暂取得 phase 等待旧 Stop 退场。实际分配和释放继续在允许的 PASSIVE_LEVEL 路径中执行。新的 Stop 先取得 phase、检查标记，之后才读取 backend。无法排空时保留完整资源并返回回滚所需状态。

该修复关闭了分配账本的并发访问窗口，保留原有无法安全退出虚拟化时的保护行为。

### 蓝屏诊断重装的写者排空

涉及 [bugcheck_control.c](../KswordARKDriver/src/features/bugcheck/bugcheck_control.c)、[bugcheck_runtime.c](../KswordARKDriver/src/features/bugcheck/bugcheck_runtime.c)、[bugcheck_context.c](../KswordARKDriver/src/features/bugcheck/bugcheck_context.c) 和内部声明头。

`TrackingReady=0` 原本只阻止后续通知，不能等待已经通过检查的通知。安装重试中的整结构清零、spinlock 初始化和 `ContextReset` 因此可能与旧写者同时执行。新增的独立 rundown 不属于被清零的诊断结构；进程通知、映像通知与正常 IOCTL 操作栈采样先取得引用，再访问缓存。安装或清理先关闭准入并等待旧写者退出，完成锁和证据初始化后才开启新代次。

等待发生在 PASSIVE_LEVEL 的串行控制路径，不在蓝屏回调里等待。崩溃现场仍读取固定、有界的非分页快照。不随安装重置的 trace ring 保持原有行为。既有 WDK 上下文回放夹具已补齐准入模拟与引用平衡检查。

### HardwareDock 和 HUD 后台任务

涉及 [HardwareDock.cpp](../Ksword5.1/Ksword5.1/HardwareDock/HardwareDock.cpp) 的 R0 健康、静态信息和传感器刷新，以及 [HudPerformancePanel.cpp](../KswordHUD/HudPerformancePanel.cpp) 的静态信息和传感器刷新。

QPointer 可以识别已经销毁的对象，但一次非空检查不会持有对象引用。旧 detached 线程的检查、页面接收器投递和失败回写之间都有窗口被 UI 线程销毁的窗口。任务现在进入全局线程池，并向应用对象排队；页面指针只在 UI 线程回调内检查和访问。Qt 6.9.3 的 `QCoreApplication` 析构在销毁 QObject 基类前等待全局线程池，因此应用接收器覆盖这些后台任务的生存期。[Qt 6.9.3 实现](https://github.com/qt/qtbase/blob/v6.9.3/src/corelib/kernel/qcoreapplication.cpp)

HardwareDock 还在 `staticOverviewChanged` 后再次检查页面是否存活，覆盖同步信号接收者中途删除页面的情况。HUD 的另一条 `QtConcurrent` 实时采样保留原实现：析构先等待 watcher，再关闭 PDH 句柄，没有确认这一条存在悬空访问。

### HTTPS 慢证书任务与异步停止

涉及 [HttpsProxyService.cpp](../Ksword5.1/Ksword5.1/NetworkDock/HttpsProxyService.cpp) 和声明头。

会话停止对每条线程最多等待 3 秒加 5 秒，但单次证书 PowerShell 执行允许 120 秒，证书锁排队还可能增加时间。旧实现清空登记表并允许服务析构，慢线程仍执行服务成员函数、访问路径和状态、释放服务内部的互斥锁。登记表中的 QPointer 也不能保证后台 wait 与 UI 删除 QThread 互斥。

证书目录、状态、锁和生成逻辑改由独立共享对象持有。停止快照持有线程强引用，超时线程继续保留到 finished。会话、异步停止和根证书准备通过共享 dispatcher 投递；服务析构首先在同一锁下关闭接收器，晚线程不再借用服务或应用对象。排队到服务的回调随服务销毁而取消。

慢任务仍可能延后退出，此修复保证其状态继续有效，没有实现立即取消所有证书脚本。服务销毁取消尚未执行的完成回调，停止期间的最后一条会话汇总也可能不送达。

### 重定向规则设置的内核栈预算

涉及 [redirect_ioctl.c](../KswordARKDriver/src/features/redirect/redirect_ioctl.c) 的 `KswordARKRedirectIoctlSetRules` 和 [redirect_runtime.c](../KswordARKDriver/src/features/redirect/redirect_runtime.c) 的 `KswordARKRedirectSetRules`。

按共享协议的 Windows ABI，完整请求为 33,824 字节，16 条规则为 33,792 字节。旧 handler 的请求快照和后端的 `newRules` 固定数组处在同一调用链，合计 67,616 字节。正常设置就会进入该调用链，风险不要求错误输入或刻意触发破坏操作。内核栈耗尽会造成致命系统错误，驱动应避免把大型数据放在嵌套栈帧里。[微软内核栈说明](https://learn.microsoft.com/en-us/windows-hardware/drivers/kernel/using-the-kernel-stack)

请求快照改为非分页池，继续保持 METHOD_BUFFERED 输入与输出共用缓冲的隔离。后端先验证所有规则，全部通过后才在锁内提交稳定快照；分配、长度或规则验证失败不会改动旧配置，已分配快照在所有后端返回路径释放。没有改变规则数量、路径长度、启用、清空和禁用的协议语义。

生产函数抽取使用 `-O1 -fno-inline -fstack-usage -Wframe-larger-than=1024 -Werror` 编译，handler 和后端报告的栈帧各为 96 字节。这是离线编译结果，不是 MSVC/WDK 实机栈深度测量，其他框架调用的栈开销需另计。

### 文件和进程监控的异步投递

新增 [AsyncUiDispatcher.h](../Ksword5.1/Ksword5.1/UI/AsyncUiDispatcher.h)，已登记主工程与 filters。投递和关闭在同一锁下交接接收器；控件析构首先关闭门禁。已入队消息还检查独立的 closed 状态，因此即使 QObject 尚未进入基类析构，也不再执行页面业务。

[FileDock](../Ksword5.1/Ksword5.1/FileDock/FileDock.cpp) 的目录解析、删除项扫描和恢复、取得所有权、IRP 提交、特殊身份运行、复制或移动、删除八个入口接入门禁。相关 detached 任务不再在后台检查 QPointer 后借用页面或应用对象。七个有限任务的完成消息附带取消收尾，覆盖投递被拒绝、已入队消息被销毁和关闭后跳过；取消恰好一次且在门禁锁外执行。

[ProcessTraceMonitorWidget](../Ksword5.1/Ksword5.1/MonitorDock/ProcessTraceMonitorWidget.Runtime.cpp) 的两种辅助进程快照、采集结束状态及自动目标更新接入同一门禁，原有 ETW 停止和析构 join 保持。门禁并不阻止已经开始的 UI 回调；安全合同仍要求控件在所属 UI 线程析构，不能从此推导任意线程删除 QWidget 的支持。

### 工作台目标的同步通知重入

涉及 [WorkbenchTarget.cpp](../Ksword5.1/Ksword5.1/UI/MemoryWorkbench/WorkbenchTarget.cpp) 的 `onDockAttached`、`onDockDetached` 和 `requestIdentity`。

这三个入口更新 liveness 为 Unknown 时会同步通知订阅者，订阅者可能关闭宿主并销毁目标。旧代码随后继续执行 `applyMaskSideEffects`，访问已经释放的 tracker 和模块目录。新增的通知后 QPointer 检查使销毁场景立即返回，不再处理后续身份副作用；正常身份变更和目标锚点语义保持。

`evaluate` 的类似疑点经追踪无效会话与 Core 的 NoTarget 拒绝后排除，没有列为确定崩溃或修改该函数。既有 wpI 夹具补入三个真实 Qt 删除场景，但本机未执行该 Qt 夹具。

## 按用户要求保留的行为与边界

### 实验性 Bugcheck Guard 修改内核代码

位置为 [bugcheck_guard.c](../KswordARKDriver/src/features/bugcheck/bugcheck_guard.c) 的 `KswordARKBugcheckGuardEnableLocked`、Hook 和释放路径。

非 HVCI 模式下，启用会通过 MDL 别名修改 `KeBugCheckEx` 的 12 字节入口。Windows x64 的内核代码修改属于完整性保护风险，可能导致 `0x109 CRITICAL_STRUCTURE_CORRUPTION`；关闭 HVCI 不等于关闭其他内核完整性保护。[微软 0x109 原因说明](https://learn.microsoft.com/en-us/windows-hardware/drivers/debugger/bug-check-0x109---critical-structure-corruption)

忽略错误模式会从原本不返回的 BugCheck 路径返回，源码也明确承认这不修复故障、不能为调用者提供可靠继续执行状态。另一个需要处理的卸载边界是 `GuardUninitialize` 记录恢复或繁忙失败后返回，而顶层卸载继续；若入口或执行中的 Hook 仍引用驱动映像，存在释放后执行风险。

这是需要显式启用的实验功能，不是本轮确认的普通启动触发器。此次未增强 Hook 或忽略能力，也未改变该实验功能的行为；其风险仍保留。稳定发行的处理方向是退出内核补丁路径，仅保留公开回调提供的有界观察窗口。

### HVM 睡眠转换主动触发保护性蓝屏

位置为 [hvm_runtime.c](../KswordARKDriver/src/features/hvm/hvm_runtime.c) 的 `KswordARKHvmPowerStateCallback`，以及 [hvm_svm_nested_machine.c](../KswordARKDriver/src/features/hvm/hvm_svm_nested_machine.c) 的嵌套停止准入。

离开 S0 时，如果 Stop 返回 `STATUS_DEVICE_BUSY` 或仍有 resident CPU，现有代码会调用 `KeBugCheckEx(0x20001)`。AMD 嵌套存在 L2、仍持有虚拟 EFER.SVME 或 HSAVE 的内层 VMM，或有待投递事件时，停止准入会拒绝退出。因此常驻 AMD 嵌套运行期间睡眠，仍可能触发这一保护行为。

本轮修复准备和释放的资源竞态，没有取消无法安全退出时的硬件保护。关闭该风险需要在目标硬件或隔离虚拟机验证全核停止、电源转换和嵌套所有权交还，不能单纯删除 BugCheck 调用。

### 线程终止 APC 的卸载排空早于回调返回

位置为 [thread_apc.c](../KswordARKDriver/src/features/thread/thread_apc.c) 的 `KswordARKReleaseThreadTerminateApcContext` 和 `KswordARKThreadApcUninitialize`。

最后一个上下文从注册表移除时就设置 DrainEvent。之后释放路径仍需要清理字段、释放 spinlock、归还线程引用和释放上下文；调用它的 APC 或工作项也仍在驱动函数中。卸载线程等到事件后，不能因此证明这些 CPU 已经离开驱动映像。

静态执行交错已经显示该保证不足，尚未在本机触发真实卸载蓝屏。这一问题未在本轮修复；需要覆盖内核回调返回边界的映像生命周期方案。仅把事件向后移动几行仍不能证明回调已经返回，不能当作修复完成。

## 保留并核对的防护

GPU 可选遥测仍拒绝 build 小于或等于 17763 以及未知版本；打开适配器后，驱动模型版本查询失败或低于 WDDM 2.4 时关闭句柄并返回。节点数量查询失败或为零时不猜测节点 0，查询预算为 64。欢迎页范围不启动节点性能、额外硬件详情或 CPU 传感器采集。静态摘要与周期遥测继续串行。这是源码防护核对，不能代表所有新系统和显卡驱动通过实机验证。

Taskbar CPU 和网络采样退出时先停止再 join；ARKLight ETW controller 停止会话后 join。它们本轮没有确认与 HardwareDock 相同的 detached 页面引用问题。ARKLight 的其他共享异步状态、API Monitor、ETW 解析及若干 UI 回调做了重点抽查，没有逐行覆盖全部模块。
