# 内存编辑/显示器重写 —— 最终综合设计

来源：design-A-risk-first.md / design-B-ux-first.md / design-C-engineering-first.md（三份均已读取全文）+ judge-safety-judge.md / judge-feasibility-judge.md / judge-ux-judge.md（三份评审均已读取全文，无缺失）。

## 0 综合结论与评审分歧点

**三份评审对总排名基本一致**：安全视角 C(9/9/7/9/7)>A(7/8/9/7/6)>B(6/5/5/5/9)；可行性视角 C(9.0均值)>A(8.0均值)>B(6.4均值)；仅 UX 对标视角把 B 排第二（因 B 在"真虚拟化翻页+常驻数据解释器"两项最扎实），但即便该评审也承认 B 的 migrationRisk/repoConventionFit 短板是"真实独立存在的代价"。**最终结论：以方案 C 的 Core/UI 分层架构与状态机为骨架**（三份评审一致认可其 invariantCoverage/decisionCompliance/repoConventionFit 最优），**吸收 A 的迁移纪律与 B 的具体 UX 设计点**，不简单选边。

**关键分歧点与取舍**：

1. **D4 范围是否可以分期打折扣**：B 明确把 FileDock/NetworkDock×2/DiskEditorTab 的迁移推到"后续非强制"阶段，三份评审中两份（safety/feasibility）把此列为 B 落败的核心原因。**采用 A/C 的做法**：D4 对 9+4 全部宿主的最终迁移与旧控件删除是强制终态，不是可选项；**舍弃 B 的范围收窄**，因为这直接违反用户已拍板的"不是新旧并存、最终要能被完全删除"。
2. **连续地址空间：真虚拟化 vs 窗口化分页**：A 采用"阶段性妥协"的窗口化分页，三份评审一致认为这是 UX 能力上限最低的做法。**采用 B/C 的 `FetchWindow` 懒扩展真连续地址空间，舍弃 A 的窗口化妥协**；但**采用 A 的纪律**——窗口/缓存具体数值参数在 Phase 0 离屏基准验证前不得定稿，这是 A 独有的诚实风险暴露，C 原方案缺失此门槛。
3. **数据解释器是否只是编辑入口**：C 把"数据解释器"写成编辑手势的一个入口，缺少常驻展示面板，UX 评审专门指出此短板。**采用 B 的 `DataInspector` 具体规格**（常驻右侧、跟随光标、i8~u64/f32/f64/指针/FILETIME/GUID/字符串、字节序分组持久化），整体移植进 C 的工作台布局，不新增写入链路、不影响安全关键路径。
4. **写入模式切换时"未提交块"如何处理**：A/C 原方案只描述两种模式共用同一管线，未处理切换瞬间的边界情况；B 是三份里唯一给出显式三选一确认（应用/丢弃/取消）的方案。**采用 B 的做法**，补进 C 的 `MemoryWriteTransaction`。
5. **Phase 粒度**：A 的 7 阶段+3a/3b/3c 子步骤比 C 的 4 个粗阶段更细，两份评审（safety/feasibility）都指出应吸收。**采用 A 的阶段粒度，套用 C 的 Core-first 顺序**。
6. **书签是否与搜索结果合并为统一列表**：仅 UX 评审提出此点，其余两份未提及，且不触及安全关键路径，复杂度增量可控。**采纳**：把 C 的 `MemoryAddressBook` 扩展为含 `kind∈{Search,Bookmark,Watch}` 的统一模型，不新增写入风险。

## 1 最终整体架构

```

  HexCanvas(+Input/FindBar) ── HexInspectorPanel(常驻,跟随光标) ── MemoryWorkbenchView(.Backend/.Disasm/.Compare/.Toolbar)
          │ 只读 Core 状态，发回调                                              │ 绑定 Core，调旧 MemoryAccessBackend
          ▼                                                                    ▼
Core 层 shared/evidence/memory_workbench/（Qt-free 且 Win32-free：仅 std::vector<uint8_t>/std::string/std::map，因为 KswordARKLightTests 工程不链接 Qt；Qt 类型转换只在 UI 层适配。已核实该工程仅 C++20、无 Qt 属性）
  MemoryTargetSession（scope/pid/attachGeneration/channel/ddmaGeneration/sourceRevision/contentRevision）
  MemoryAddressExpr   MemoryWriteTransaction(含 pendingOverlayGuard)   MemoryDiffOverlay
  HexViewport(FetchWindow懒扩展)   Int3PatchLedger   MemoryAddressBook(统一Search/Bookmark/Watch)
```

## 2 最终数据模型（目标会话）

```cpp
struct MemoryTargetSession {               // Dock 持一份权威，各宿主只持只读拷贝+代次比较
  enum class Scope { ProcessVirtual, KernelVirtual, Physical };
  Scope scope; DWORD pid; quint64 attachGeneration;
  MemoryAccessBackend::Channel channel;    // 四选一枚举，无"自动"选项
  quint64 ddmaGeneration;
  quint64 sourceRevision;    // 仅换目标/重读时 ++（取舍点3的根治：editor.md "快照代次实为内容代次"）
  quint64 contentRevision;   // 仅编辑/撤销时 ++，两者独立，陈旧回调须两者皆核对
};
struct MemoryDiffOverlay {                 // 取代 ME 的 m_original/m_observed/m_previousRead/m_recentChanges
  QByteArray baselineBytes; QMap<quint64,QByteArray> stagedPatches;  // 稀疏 offset→bytes
  bool hasPendingPatches() const;          // 供 D1 模式切换确认使用
};
class MemoryWriteTransaction {             // 状态机，立即写/暂存写共用
  enum State { Idle, Staged, ConfirmPending, Writing, Verifying, Committed, Failed, RolledBack };
  enum ConfirmKind { UiConfirm/*可跳*/, ProtocolConfirm/*不可跳,审计日志*/ };
  enum DdmaApprovalScope { ThisBlock, RestOfBatch };  // 修复 DR-02：用户在确认框显式选择，不再循环外隐式复用
  bool pendingOverlayGuard(WriteMode from, WriteMode to) const; // D1 切换时存在未提交块则必须先弹三选一
};
```

## 3 最终 Hex 视图设计（D4 四类宿主接入）

`HexViewport`(Qt-free)：行按 16 字节对齐，**首行按偏移补空位**（采用 B 的具体实现细节，修正地址错位 H09/V-09，A/C 原方案只说"对齐"未提这一步）；`FetchWindow{start,length}` 按视口滚动懒扩展+LRU 页缓存，真连续地址空间，非窗口化妥协；`bytesValidMask` 标记部分读，渲染 `??` 不补零。`HexCanvas`(自绘 QWidget)只渲染可见行，对象数 O(可见行数)。单一 `SelectionRange{anchor,caret,activePane}`。编辑手势（nibble 流式输入、ASCII 直接编辑、Ctrl+V 按字节序粘贴、选区填充/NOP、类型化写值）统一经 `HexCanvasInput` 落到 `MemoryDiffOverlay::stage()` 一个入口。**`HexInspectorPanel`**（采用 B 的规格，常驻右侧）：跟随光标显示 i8/u8~i64/u64、f32/f64、指针(模块+偏移)、FILETIME/time_t/GUID、字符串(ASCII/UTF-16LE)，字节序与分组持久化到 `QSettings`，取代"选区长度决定能看到什么类型"的现状缺陷。

| 宿主类别 | Provider | 关键约束保留方式 |
|---|---|---|
| 内存工作台(Workbench/Hvm/Hook/Dump) | `MemoryTargetSession`+分页异步读 | 连续地址空间+暂存叠加层独立于读窗口，翻页/重读不丢改动；驱动单次读取仍守既有 1MiB 上限与回绕/空区间校验（原样从 `driverReadMemoryFromUi` 搬入） |
| FileDock | 只读文件窗口 Provider | 原样保留 64KiB-2MiB+世代票据，仅换渲染内核为 `HexCanvas` |
| NetworkDock×2 | 只读字节数组 Provider | `HexFindBar`+显式 `QAction`(图标+tooltip) 内置满足 Ctrl+F/G/复制/导出 |
| DiskEditorTab | 整盘 Provider | 整盘可写回+系统盘二次确认留在宿主层（不变式1），写路径走本地文件语义的精简 `MemoryWriteTransaction` 子状态机，不接驱动四通道 |

迁移路径：`HexEditorWidgetAdapter` 先替换内部渲染实现、外部调用点签名不变；`HexEditorWidget.h` 本身不改一行，避免 7 分钟级扇出重编译提前触发。

## 4 最终内存工作台设计（Tab3+Tab5 合并，D1）

布局自上而下：①会话条（scope+四通道单选，不可用置灰给原因 tooltip，不自动回退）；②地址条（`MemoryAddressExpr` 统一解析 0x/裸十六进制/module+offset/反引号，地址默认十六进制、数量默认十进制分离）+ **D1 写入模式开关**（图标化 ToggleSwitch，默认 Immediate）；③主体：`HexCanvas`(连续地址空间) + `HexInspectorPanel`(常驻右侧) + 可展开的统一地址列表侧栏；④反汇编/文本(`CodeEditorWidget`，去掉违规 `QPlainTextEdit`)/对比(基线改为"上次读取")三子页；⑤单一状态条。字节表上方横带从现状 ≥7 条收到 2 条。

**D1 落实**：两种模式共用同一条 `MemoryWriteTransaction` 管线（Staged→ConfirmPending→Writing→Verifying→Committed，失败不报整体成功），区别只在触发时机：Immediate 下编辑完成即自动走一次完整流程；StagedThenApply 下编辑只 `stage()`，显式"应用"按钮触发。**切换边界（采用 B 的设计）**：开关切换前若 `MemoryDiffOverlay::hasPendingPatches()==true`，强制弹"先应用这些改动，再切换？应用/丢弃/取消"，不允许静默应用或丢弃。暂存叠加层的"应用"复用 driverrw.md 已核实的三条既有分支（物理4KiB切片/VA逐块回读终止/DDMA本轮同意选择），本次不重写其内部实现。

## 5 断点/书签/后端条的最终处理（D3）

**Int3 补丁**：`Int3PatchLedger`(Qt-free)，`PatchEntry{pid,attachGeneration,address,originalByte,installedAt}`；UI 文案改"int3 补丁"/"写入·还原单字节(0xCC)"，去掉 `hitCount` 与"中断"语义；**用户已拍板：保留现状零摩擦操作，不复用内存编辑的二次确认链路**（舍弃 B 的要求——写入/还原单字节维持一键直达，不经 `MemoryWriteTransaction.ConfirmPending`；代价是这条路径确实比其余写入操作少一道核对，属于用户已知并接受的风险）；detach/关闭按 `attachGeneration` 批量还原；额外暴露"存在未还原补丁"查询供退出前提示（C 独有细节，A/B 均无，保留）。

**地址簿**：`MemoryAddressBook` 扩展为统一模型，字段 `{kind∈{Search,Bookmark,Watch}, module, rva, note, valueType}`（采纳 B 的 `AddressListModel` 思路，合并进 C 的类而非新开一套并存表），module+offset 存储换进程不指错，值可按类型编辑；刷新定时器按 `isVisible()` 门控，不再无条件常跑；与搜索共用丢弃陈旧结果的代次机制。

**后端选择条**：Dock 级单一 `ChannelSelector` 直绑 `MemoryTargetSession.channel`，四通道不自动合并/回退，默认值与按钮文案一致（修复"R0读取实走R3"）。

## 8 迁移阶段划分（吸收 A 的细粒度，套用 C 的 Core-first 顺序）

- **Phase 0 修订（2026-10-02，实现前核对所得）**：①Core 一律用标准库类型，命名空间 `ksword::memwb`；②`MemoryEditHistoryCore`/`MemoryAssemblyCore` **本阶段不搬迁**——二者已是 Qt-free 且各有 g++ 脚本覆盖（420/250 项），搬迁没有读数要求，且汇编核心依赖 Zydis，并入 Light 工程要多编一个第三方 C 文件；留在 `UI/` 原位，等有需要再议；③FetchWindow/LRU 的参数先作为带"暂定"标注的 constexpr，纯 C++ 缓存命中基准在 Phase 0 做，涉及 Qt 渲染的离屏基准随 Phase 1 的 HexCanvas 一起做。
- **Phase 0**：建齐 7 个 Core 类+7个测试套件注册（先于重写钉死旧行为，尤其写入确认顺序/二次核对时机）；**离屏Qt微基准验证`FetchWindow`/LRU缓存大小参数，不通过不得定稿数值**（采自A，C原方案缺此门槛）。回退：删新目录，零风险。
- **Phase 1（2026-10-03 修订，路线收敛）**：不再做"适配层与旧控件并存、Phase 6 才删旧控件"，改为**原地替换 `HexEditorWidget` 的内部实现**——类名与公开 API 保留（全仓 13 个使用者调用点一行不改，`TextSearchReplaceSupport` 靠类名判断"自带查找栏"也继续成立），内部整体换成新的 `HexView` 复合控件，旧的约 3700 行表格实现整体删除。理由：①旧控件在 2 MiB 数据上整表重建实测 2.3 s、全选后设画刷 0.97 s（离屏夹具对照基线，机制同旧控件）；②旧 API 外部实际只被用到约 13 个函数（`setRegionData/jumpToOffset/jumpToRow/selectedBytes/selectionRange/setChangeBaseline/SearchMode` 全仓零调用，可直接删）；③更符合 D4"旧控件全仓退役"的本意。分步：1a 自绘 `HexCanvas`+`HexInspectorPanel`+`MemoryValueDecode`（已完成并验证）→ 1b-i `MemoryByteSearch`+画布接口补全+`HexView`/查找条/跳转条/导出/旧缓冲模型兼容层（已完成并验证）→ 1b-ii 门面替换+主程序登记+i18n+主程序构建（进行中）。回退：git revert 该提交即回到旧控件。
  - 旧控件→新控件的语义对应：`setByteArray(bytes, base)`→`HexView::setBuffer(base, bytes)`（注意参数顺序相反）；`setByteAtAbsoluteAddress`→`setByteQuiet`（不发 `byteEdited`，回滚路径依赖）；`setChangeReferences`→`setReference`；`byteEdited` 仍只在用户编辑时对每个变化字节恰好发一次。
  - 后续待办：直接使用 `HexView`（不经 `HexEditorWidget` 门面）的新宿主，须把 `HexView` 加进 `TextSearchReplaceSupport.cpp` 的 `hasOwnFindPanel` 类名白名单；画布高亮层颜色不随主题（由 `HexView` 在主题变化时重设）。
- **Phase 2**：`MemoryAddressBook`(含统一列表)作独立面板接入搜索与书签，与旧表并存比对。回退：开关隐藏新面板。
